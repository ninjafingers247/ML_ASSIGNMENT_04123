# Data Versioning & Lineage (DVC)

RecoMart's data and pipeline lineage is versioned with **DVC**, initialized as a
subdirectory repo (`dvc init --subdir`) inside `recomart_pipeline/` within the
same git repository.

## Setup

```bash
cd recomart_pipeline
dvc init --subdir
mkdir dvc_local_remote
dvc remote add -d localremote ./dvc_local_remote   # local-directory "remote", no cloud account needed
```

## What's tracked, and how

| Path | Tracked via | Why |
|---|---|---|
| `source_data/` | `dvc add` (plain data tracking) | The upstream vendor CSV drop — not generated by any pipeline stage, just versioned as-is |
| `data/raw/olist_csv_batch/` | `dvc.yaml` stage output (`ingest_csv`) | Regenerated by the batch ingestion script each run |
| `data/processed/` | `dvc.yaml` stage output (`prepare`) | Regenerated by cleaning/EDA |
| `data/features/`, `features/recomart_features.db` | `dvc.yaml` stage output (`build_features`) | Regenerated by feature engineering |
| `reports/02_data_quality_report.md` | `dvc.yaml` stage output (`validate`, `cache: false`) | Small text report, versioned in git directly rather than DVC cache |

`data/raw/product_signals_api/` (the near-real-time REST API ingestion) is
**intentionally outside** the `dvc.yaml` DAG: it's polled on its own short
interval (see `orchestration/prefect_flow.py`), not a deterministic batch step,
so it isn't a natural fit for `dvc repro`'s one-shot dependency graph. It's still
a plain filesystem path DVC-aware tools can diff/version if needed.

## Pipeline stages (`dvc.yaml`)

```
source_data.dvc -> ingest_csv -> validate
                              -> prepare -> build_features
```

Run the whole thing (only re-executing stages whose deps changed):

```bash
dvc repro
dvc dag        # ASCII view of the stage graph above
```

Each stage's exact command, dependencies, and outputs (with content hashes) are
captured in `dvc.lock` — regenerated by every `dvc repro`, and diffable in git to
see exactly what changed between runs (e.g. `git log -p dvc.lock`).

## Metadata tracked per version

- **Data source**: `source_data.dvc`'s hash pins the exact upstream CSV snapshot.
- **Date of ingestion**: each `ingest_csv`/`ingest_api` run stamps its output
  partition folder with `data/raw/<source>/<type>/<YYYYMMDD_HHMMSS>/`, and writes
  a JSON manifest (`_manifests/manifest_<ts>.json`) with row counts and sha256
  checksums per file — see `ingestion/ingest_csv_sources.py` and
  `ingestion/ingest_api_source.py`.
- **Applied transformations**: `dvc.lock` records each stage's command string and
  input/output hashes, so `git diff dvc.lock` shows exactly which transformation
  changed and what data it produced.

## Example lineage commands

```bash
dvc push                 # sync data + cache to the local remote
dvc pull                 # restore data on a fresh checkout
dvc diff HEAD~1           # what data changed since the last commit
git log -p dvc.lock       # history of pipeline command/hash changes
dvc status                # what's out of date vs. the current workspace
```
