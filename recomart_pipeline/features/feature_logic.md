# RecoMart Feature Dictionary

Generated by `features/build_features.py` from `data/processed/interactions_prepared.parquet`
(batch CSV pipeline) and the latest `product_signals_api` ingestion (REST API pipeline).
Stored in both SQLite (`features/recomart_features.db`, schema in `schema.sql`) and
parquet under `data/features/` (consumed by the Feast feature store).

## `interactions`
| Feature | Source | Definition |
|---|---|---|
| `review_score` | order_reviews | Raw 1-5 rating, the explicit feedback signal used for collaborative filtering |
| `price_norm` | order_items | Min-max normalized item price at time of purchase |
| `freight_value_norm` | order_items | Min-max normalized shipping cost |
| `timestamp_norm` | orders | Min-max normalized purchase timestamp (recency signal) |

## `user_features` (entity: `customer_unique_id`)
| Feature | Definition |
|---|---|
| `user_interaction_count` | Count of distinct rated purchases — user activity frequency |
| `user_avg_rating` | Mean `review_score` given by the user — rating tendency/bias |
| `user_avg_spend` | Mean item price across the user's purchases |

## `item_features` (entity: `product_id`)
| Feature | Source | Definition |
|---|---|---|
| `item_interaction_count` | interactions | Count of ratings received — item popularity within our own data |
| `item_avg_rating` | interactions | Mean rating received by the item |
| `category_encoded` | products | Label-encoded English product category |
| `api_popularity_score` | product-signals API | Order volume normalized against the catalog max, refreshed via near-real-time polling |
| `api_sentiment_score` | product-signals API | Lexicon-based polarity over review comment text, in [-1, 1] |
| `api_avg_price` | product-signals API | Average price observed for the item across all its orders |

## `item_cooccurrence`
Top 5,000 `(product_id_a, product_id_b)` pairs by how often the same user rated
both items, used as a simple similarity signal for content-adjacent/co-purchase
based recommendations (complements the SVD-based collaborative model).

## Freshness / versioning
Every table carries an `event_timestamp` set at build time, which Feast uses for
point-in-time correct retrieval — training pulls the feature values as they stood
at each interaction's timestamp, and inference pulls the latest materialized
values (see `feature_store/demo_retrieval.py`).
